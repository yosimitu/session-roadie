# 設計

re:Roadie（パッケージ名 `session-roadie`）の設計方針と、機能ごとの設計です。使い方は [README](../README.md) を参照してください。

## 1. 構成と方針

**目的:** re:Invent 参加者の意図とプロフィールをもとに、AWS Events API（REST）でセッションの計画・予約・移動時間の確保・変更の追従を行い、結果を公式アプリの個人スケジュールに書き戻すローカルのエージェント。

**構成:** Node.js / TypeScript 製。AWS Events REST API に、Builder ID の OAuth 2.0 Authorization Code + PKCE でサインインします。ローカルの JSON ストアに、カタログのスナップショットと、プロフィール・意図・メモを保持します。書き込みは「意図」を唯一の情報源にし、`GetSchedule` との再照合で冪等に収束させます。

**使用技術:** TypeScript、Node.js 22 以上（プレーンな JSON ストア）、`commander`（CLI）、`open`（ブラウザ起動）、`vitest`（テスト）、標準の `fetch`、`@modelcontextprotocol/sdk`（MCP サーバー）。

**守っていること（制約）**

- ホスティングしない。全機能は、利用者のローカルマシンで動作する。
- カタログデータをリポジトリにコミットしない。プロフィール・意図・メモもローカル保存のみで、サンプルはダミー値にする。
- クォータを厳守する。`ListSessions`/`GetSession` 120 回/分、`GetSchedule` 60 回/分、書き込み系 30 回/分（セッション単位）。`429` は `Retry-After` に従ってリトライする。
- 書き込みは冪等に再照合する。`GetSchedule` を都度取り直し、意図との差分だけを送る（公式ドキュメントの「Retrying a write safely」に沿う）。
- `ListEvents` は ongoing/upcoming のみ返るため、会期中にローカルスナップショットを保存しないと、帰国後の機能が成り立たない。

**層の分け方**

```
Claude Code → スキル/コマンド（手順だけ） → re:Roadie（ロジックは全部ここ） → AWS Events REST API
```

- **意図の解釈は LLM（Claude Code）側、決定的なロジックは re:Roadie 側**という役割分担にしています。差分計算、冪等な再照合、移動時間の計算、クォータ制御、代替の判定は、すべて re:Roadie にあります。
- MCP サーバーの内部に、Bedrock などの LLM 呼び出しを埋め込む設計は採っていません。Claude Code 自身が推論を担うため二重になること、Bedrock は別途 AWS アカウントと IAM 権限が必要で、設置の手間が増えることが理由です。
- 書き込み系ツールは、`*_plan`（差分を見せるだけで実行しない）と `*_apply`（実行する）に分けています。CLI の確認プロンプト（`-y`/`--yes`）に当たる「確認してから実行する」動作は、MCP 越しでは、クライアント側（スキル経由の Claude）が担います。
- `.mcp.json` でプロジェクトスコープの MCP サーバーとして登録し、`.claude/skills/re-roadie/SKILL.md` には、ツールを呼ぶ順番の手順だけを書きます（ロジックはスキル側に持たせません）。

**時刻の扱い**

- 個人予定の日時は、UTC ではなく会場の現地時刻（PST、UTC-8 固定）のまま書き、読むときも保存値を現地時刻として扱います。公式アプリが保存値をそのまま表示するためです。
- `GetEvent` の `startDate`/`endDate` のオフセット（`-08:00`）を信頼し、`timezoneAbbreviation` は使いません（`src/schedule/sessionTimeUtc.ts`）。

## 2. 失敗パターンと、テストで固定していること

実装前に洗い出した失敗パターンは、テストで固定しています。

- 部分成功（`BulkResult.failed`）を無視して、「全件成功」と誤表示する。
- `429` を受けて、リトライせずに失敗扱いにする（`Retry-After` を守らないと、信用低下のリスクがある）。
- `CreatePersonalTime`/`UpdatePersonalTime` の 5 分刻みの制約を無視して、`400` になる。
- 書き込みのタイムアウト後に、同じリクエストを再送して、`CreatePersonalTime` が二重に登録される。
- プロフィール・意図・メモのファイルが無いときに、全機能が落ちる。
- `title`/`description` に半角の `[` `]` を含めて、`400` になる。
- 成功レスポンスに `personalTimeId` が無く、直後に `GetSchedule` を呼ばないと、新規エントリを特定できない。

## 3. エラー処理の設計

想定外の応答が来たときに原因を追えるよう、次の 3 点を設計に入れています。

1. エラー本文を失わない。`ApiError` は `operation` と `body` を保持し、`message` は `API error ${status} (${operation})` にします。MCP は `toRoadieError` の結果を JSON で返し（`isError: true` を維持）、CLI は「エラー」「次にすること」と、body がある場合の「詳細」を表示します。
2. 途中の例外で、実行済みの工程が分からなくならないようにする。工程ごとに結果を持ちます（下の `executeReconcilePlan`）。
3. スキルの失敗時の案内を、`kind` ごとに持つ。

### エラー変換層（`src/errors.ts`）

`toRoadieError(err: unknown): RoadieError` に、変換を集約しています。

```ts
interface RoadieError {
  kind: 'authExpired' | 'notOpenYet' | 'forbidden' | 'rateLimited' | 'network' | 'unknown';
  status?: number;
  operation?: OperationName;
  message: string; // 日本語1文。原因
  hint: string;    // 日本語1文。次にすること
  body?: unknown;  // APIのエラー本文（あれば）
}
```

判定は、次の表を上から順に評価します。

| kind | 条件 | hint |
| --- | --- | --- |
| `authExpired` | `ApiError.status === 401` | `auth_login` でサインインし直して再実行する |
| `notOpenYet` | `operation` が `ReserveSessions`/`CancelReservation` で、status が 403 または 409 | 予約 API が開放前の可能性がある。お気に入り・個人予定の操作は影響を受けない |
| `forbidden` | 上記以外の 403 | 権限またはエンドポイントを確認する。body を確認 |
| `rateLimited` | 429（`QuotaLimiter` のリトライ上限を超えたもの） | 少し待って再実行する |
| `network` | `TypeError` のうち、message が `fetch failed` のもの（それ以外の `TypeError` は、バグの可能性があるため `unknown`） | 接続を確認して再実行する |
| `unknown` | 上記以外（5xx を含む） | body をそのまま提示する |

### `executeReconcilePlan` の工程分離

4 つの工程（予約、お気に入りの追加、取消、解除）を、独立に実行し、結果を工程ごとに持ちます。

```ts
type StepResult<T> =
  | { ok: true; value: T }
  | { ok: false; error: RoadieError }
  | { ok: false; skipped: true };

interface ApplyResult {
  reserve: StepResult<BulkResult>;
  favorite: StepResult<BulkResult>;
  cancelReservation: StepResult<ItemResult[]>;
  unfavorite: StepResult<ItemResult[]>;
}
```

- ある工程が例外で失敗しても、次の工程を続行する（例: 予約が `notOpenYet` でも、お気に入りの変更は実行される）。
- 失敗が `authExpired` の場合だけ、以降の工程を即中断し、`skipped` にする（以降もすべて 401 になるため）。
- 取消・解除は、セッション単位のループで、1 件の失敗で残りを止めない。
- `schedule_apply` は、実行後に `GetSchedule` を取り直して、`remainingPlan` を返す。この再照合が失敗したときは、`reconcileError` を返し、`remainingPlan` は省略する。
- CLI の終了コードは、工程の失敗・件ごとの `error`/`skipped`・`reconcileError` のいずれかがあれば 1 にする。`BulkResult.failed`（`scheduleConflict` など、API 応答上の失敗）は、従来どおり 0 のままにする。

### 既知のリスクと制限

- `notOpenYet` の判定は、403/409 に依存している。別のステータスで未開放を返す場合は、判定表の更新が必要。
- トークン無しで呼ぶと、API Gateway 既定のオーソライザーが 403 を返すことがあり、その場合は `authExpired` ではなく `forbidden` と判定される。`auth_status` を先に呼ぶスキルの手順で、回避する前提にしている。
- `apply`（reconcile）は、「あるべき状態に無いものは外す」完全な置き換えです。`AssociateFavorites` は 1 リクエストあたり `sessionIds` が最大 10 件なので、お気に入りを 10 件ずつ分けて `apply` すると、先に追加した分が外れます。10 件を超えて追加するときは、既存分を含めた累積のリストを渡します（自動のバッチ分割は未実装）。

## 4. カタログの監視（watch）

お気に入りの未予約が満席のままでも、`limited` などの空席表示が付くことがあります。公式アプリを繰り返し開かずに済むよう、変化を知らせる `watch` を用意しています。予約は実行しません。

- **取得方法:** `ListSessions` の全件取得を毎回行います（数ページ）。空席、新着、会場・時間の変更、取消が同じ取得で揃い、`GetSession` の個別取得（新着を見つけられない）より単純です。最短 5 分間隔で、120 回/分のクォータに対して余裕があります。
- **状態:** `data/watch-state-<eventId>.json` に、セッションごとの空席・会場・日時・タイトルを保存します。`watch` は、あわせて日別のカタログのスナップショットと、空席表示の履歴（`data/seat-history-<eventId>.json`）も保存します（§5、§6）。
- **イベント:** `seatOpened`（満席だったお気に入りの空席表示）、`altSeatOpened`（満席のお気に入りの再演）、`newMatching`（プロフィールに合う新着）、`changedMine` / `removedMine`（予約・お気に入りの変更と取消）。
- **初回:** 基準を保存するだけで、通知しません（新着が一度に大量に出るのを避けるため）。
- **カタログが 0 件のとき:** 状態を作らず・更新せず、スナップショットも保存しません（API が一時的に空を返す間の保護）。
- **通知:** `--notify` で、デスクトップ通知を出します。macOS は `osascript`、Windows は `powershell.exe`（Windows PowerShell 5.1）のトースト通知です。どちらも、本文と題はスクリプトの文字列に埋め込まず、引数か環境変数で渡します。それ以外の OS では、コンソール表示のみです。通知に失敗しても `watch` は止めず、警告だけ出します。
- **新着の通知:** `--notify` では、上のイベントの通知に加えて、プロフィールに合うかを問わず、新着の件数と上位 3 件（プロフィールに合うものが先、スポンサー枠は後ろ、残りは開始日時順）を、別の通知で出します。
- **部分的な応答への備え:** 取得件数が前回の半分未満のときは、状態を更新せず、イベントも返しません（`status: shrunk`）。取消の誤検知と、次回の新着の大量通知を避けるためです。同じ `sessionId` が重複して返っても、1 件に畳んでから比べます。`seatAvailability` が一時的に欠けたときは、前回の値を残します（空席から欠落を挟んで空席に戻っても、通知しません）。
- **入力の検証:** `eventId` は英数字・ハイフン・アンダースコアに限ります（状態ファイルのパスに使うため）。MCP の全ツールの入口でも同じ検証をします。
- **制限:** 前回の観測に無い再演に空席表示が出ても、`altSeatOpened` にはなりません（新着として扱い、プロフィールに合わなければ通知しません）。`catalog_watch` と `re-roadie watch` は同じ状態ファイルを共有するので、片方が確認すると、もう片方からは同じ変化が見えなくなります。

## 5. 更新履歴（digest）

カタログの変化を、あとから日ごとに見返せるようにします。読み取りだけです。

- **保存:** `sync` と `watch` は、実行のたびに、その日のカタログを `data/catalog-<eventId>-YYYY-MM-DD.json` に保存します（同じ日は上書き。日付は UTC）。`sync` は 0 件のとき、`watch` は 0 件または前回の半分未満のとき、保存しません。
- **差分:** 保存済みの日別スナップショットを古い順に並べ、隣り合う日どうしを `diffCatalog` で比べます。件数 0 のスナップショットは飛ばします。「変更」は、会場・部屋・日時に限ります（概要の文言修正まで拾うと、ノイズになるため）。
- **保存のない日:** その日をまたぐ期間は、「N 日分をまとめた差分」と注記します。間に追加されて消えたセッションは、出ません。
- **出力:** `digest` コマンドが、単体の HTML（`data/digest.html`）を書き出します。ネットワークは使いません。`view` の「更新履歴」タブは、同じ描画（`renderDigestBody`）を使い、直近 14 期間までを載せます。`watch` は、スナップショットを保存した回に、`digest.html` も作り直します。
- **言語:** 日本語と英語に対応します。英語では、会場などの区切りを `, ` にします。

## 6. 現地・予報・寄り道

現地での使い勝手と席の取りやすさを上げる 3 つです。どれも読み取りだけで、予約は実行しません。

- **`now` / `sessions_now`（いまから行けるセッション）:** 開始が「いま＋現在地からの移動時間」以降で、指定の分数（既定 90）以内に始まり、予約・個人予定と重ならず、前後の予定との間に移動時間が取れ、満席表示でないものを返します。現在地は、開催中または直近 3 時間以内に終わった予約の会場から決めます。実際の時刻は `sessionStartUtc` と同じ基準（会場の現地時刻を UTC に直した瞬間）で比べるので、`new Date()` をそのまま使えます。`--at` で現地時刻を指定すると、会期外でも試せます。`walkUp` は、当日会場で並ぶ形式として扱います。
- **`forecast` / `seat_forecast`（満席予報）:** 空席表示を 0（available）〜3（unavailable）の段階にそろえ、最初と最後の観測の差を日数で割った速さから、満席までの日数を見積もります。統計的な予測ではありません。履歴は、`sync` が毎回保存する日付別スナップショット（空席表示のあるもの）と、`watch` が記録する `data/seat-history-<eventId>.json` を合わせたものです。観測が 3 日未満、または 3 日以上でも期間が短いうちは `confidence: low` です。
- **`detour` / `detour_suggest`（寄り道）:** トピックごとに関心の強さを数えます（プロフィールで宣言した関心は 3、予約は 1 件ごとに 2、お気に入りは 1 件ごとに 1）。セッションの強さは、トピックのうち最大のものです。強さが 3 以下で、予約の合間に収まるものを、強さの小さい順、空席の多い順、予約と形式が違う順、移動が短い順、時刻の早い順に並べます。ランダムは使わず、同じ入力なら同じ結果です。トピックの種類が少なく、完全に関心の外のものだけに絞ると、候補が出ない日が多くなるため、3 以下まで許しています。

## 7. カタログの傾向（trends）

`trends` / `catalog_trends` は、カタログの傾向を出します。読み取りだけです。

- **数えるもの:** 話題、サービス、形式、レベル、日別の件数と割合。基準日があれば、その日からの増減、新しく載った・消えたセッション数（`sessionId` の出入り）、増えたサービス、タイトルに増えた語。`--keyword` で指定した語の件数。予約とお気に入りのトピックの割合を全体と比べ、多い／少ない話題を 3 件ずつ。
- **基準日:** 保存済みの日付別スナップショット（`sync` と `watch` が保存）。省略時は最も古い日。
- **語の拾い方:** タイトルを英数字で分け、2 文字以上・数字だけでない・除外語（`the`、`aws`、`amazon`、`build` など）以外を数えます。自動で拾うのは、現在 5 件以上のタイトルに出る語だけです。別の言い方（`AI agents` と `agentic`）は同じ語として数えません。
- **レベルの表記ゆれ:** スナップショットによって、`300 - Advanced`（ハイフン）と `300 – Advanced`（en ダッシュ）が混在します。そのまま数えると、全レベルが「新しく載った」ように見えるため、先頭の 3 桁で数えます。
- **解釈の注意:** 件数はカタログの掲載数です。AWS の注力、参加者数、公開の順序を表すとは限りません（非公開から公開になっただけで増えることもあります）。件数が動かない話題を、関心の低さとは読めません。
- **サインインできないとき:** 傾向そのものは出し、予約・お気に入りとの比較だけを省いて、理由を `notes` に書きます。

## 8. 開始の10分前までに着く

公式 FAQ（`aws.amazon.com/events/reinvent/faqs/`）の次の案内を、判定に反映しています。

- 予約した席は保証されません。**開始の10分前までに部屋に着かないと、席は当日並ぶ人（walk-up）に譲られます。**
- 各セッションは、当日並ぶ人向けの席を一部残しています。予約できなかったときの案内は「再演（`-R`）を探す、空きを確認し続ける、現地の列に並ぶ」です。
- 会場間のシャトルは、会期中は走り続けます（バッジが必要）。会場間は余裕を見るよう案内があります。

反映のしかたは、次のとおりです（定数は `ARRIVAL_BUFFER_MINUTES = 10`、`src/schedule/travelTime.ts`）。

- **連続するセッションの間隔:** 「移動時間 + 10分」を要求します。同じ会場でも、終了と同時に次が始まる組み合わせは成立しません。対象は、`travel-blocks` の不足判定、`schedule_optimize` の組み合わせ判定、おすすめ（`recommend`）の重なり判定、`now` と `detour` の収まり判定です。個人予定との間には、重ならなければよいとしています（会場も席の取り置きもないため）。
- **最低空き時間（`minGapMinutes`）との関係:** 大きい方を要求します。`relaxed`（30分）と `normal`（15分）は、同じ会場では変わりません。別会場の組み合わせは厳しくなります。
- **`considerTravelTime: false` のとき:** 到着の余裕も見込みません（移動時間を考慮しない指定を尊重するため）。
- **移動時間ブロックの長さ:** 必要な移動時間だけ（5 分刻みに切り上げ）で、位置は前のセッションの終了直後です。余裕の10分は空けておきます。
- **`now` の満席表示:** 本体から外さず、別枠（`queue`）に出します。現地の列に並べば入れる場合がある、という公式の案内に沿った扱いです。席は保証されないので、注記を付けます。
- **移動時間の表:** `src/schedule/travelTime.ts` の表は、公式のキャンパスマップ（縮尺なしの模式図）の位置から読み取った推測値です。
